1La historia: el cabo suelto de la saga

Minutos 0 a 10 · se platica en grupo; tú solo lees y miras el código.

Lo que dejó la S08

En la S08 la transferencia se volvió una saga: cargo, abono, asientos. Si el abono falla, se devuelve el cargo y el dinero regresa. Cada paso se guarda en la base con su estado.

Pero queda un cabo suelto. Al final, después de que el dinero ya llegó a destino, la saga llama por HTTP a notificacion y espera su respuesta. Abre transferencia/.../TransferenciaService.java y busca LAB S09:

// 05-mensajeria-base · TransferenciaService.transferir (resumido)
t.marcarAbonada();
t = guardar(t);                        // el dinero YA llegó a destino
movimientos.registrar(...);            // asientos del ledger
notificaciones.notificar(cargo);       // HTTP a notificacion: espera respuesta
notificaciones.notificar(abono);       // si notificacion está caído, la excepción sale de aquí
t.marcarCompletada();                  // ...y esta línea nunca se ejecuta
return guardar(t);

Si notificacion está caído, la transferencia que ya movió el dinero responde con error y se queda en ABONADA para siempre. Un aviso, que puede esperar, tumba una operación que ya estaba hecha.

Llamada telefónica contra buzón

Hoy transferencia llama por teléfono: si nadie contesta, no puede seguir. Lo que vamos a hacer es dejar un recado en un buzón. Transferencia publica un hecho, "esta transferencia se realizó", y sigue con lo suyo. Notificación lo lee cuando puede. El buzón es un broker de mensajes: RabbitMQ.

→HTTP, y espera
notificacionsi está caído: error

Antes: transferencia depende de que notificación esté arriba en ese instante.

→transferencia.realizada

Después: el recado espera en la cola. Lo naranja es lo que vas a construir.

Dos piezas de RabbitMQ que vas a usar:

  • Un exchange es la ventanilla donde se dejan los mensajes. No guarda nada: según la routing key de cada mensaje, decide a qué colas mandarlo. El nuestro es de tipo topic: las colas se enlazan con patrones como transferencia.*.
  • Una cola sí guarda. Es de quien consume: notificación tiene la suya y ahí esperan sus mensajes aunque esté apagado.

El contrato del evento

Usa exactamente estos nombres. Así cualquier compañero puede conectar otro consumidor a tu broker, y así se revisa tu entrega.

PiezaValor

transferencia.revertida (la saga llega a COMPENSADA)

3Publicar el evento

Minutos 20 a 40 · todo esto pasa en el servicio transferencia.

Vas a hacer que transferencia, al terminar la saga, deje un recado en el exchange transferencias en lugar de llamar a notificación. Son seis pasos: el id del evento, el evento, la configuración, el publicador, la saga y la prueba.

3.1 · Que cada transferencia nazca con su eventoId

El eventoId tiene que ser el mismo si el evento se publica dos veces. Si lo generaras al publicar, cada reintento parecería un evento nuevo. Por eso nace con la fila y se guarda con ella. Abre transferencia/src/main/java/mx/mexibanco/transferencia/Transferencia.java y agrega lo verde:

3.2 · El evento

El evento es el contrato con quien escuche, así que es un record propio y no la entidad Transferencia: cambiar una columna no debe romper a nadie afuera. Es un hecho en pasado ("ya se hizo"), no una orden. Crea el paquete mensajeria y, dentro, transferencia/src/main/java/mx/mexibanco/mensajeria/EventoTransferencia.java:

package mx.mexibanco.mensajeria;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.UUID;

public record EventoTransferencia(UUID eventoId, String tipo, Long transferenciaId, String clabeOrigen,
                                  String clabeDestino, BigDecimal monto, BigDecimal saldoOrigen,
                                  BigDecimal saldoDestino, Instant fecha) {

    public static final String REALIZADA = "TransferenciaRealizada";
    public static final String REVERTIDA = "TransferenciaRevertida";

    /** La saga llegó a COMPLETADA: el dinero salió de origen y llegó a destino. */
    public static EventoTransferencia realizada(UUID eventoId, Long transferenciaId, String clabeOrigen, String clabeDestino,
                                                BigDecimal monto, BigDecimal saldoOrigen, BigDecimal saldoDestino, Instant fecha) {
        return new EventoTransferencia(eventoId, REALIZADA, transferenciaId, clabeOrigen, clabeDestino, monto,
            saldoOrigen, saldoDestino, fecha);
    }

    /** La saga llegó a COMPENSADA: el abono falló y el cargo ya regresó. Destino no se tocó: sin saldoDestino. */
    public static EventoTransferencia revertida(UUID eventoId, Long transferenciaId, String clabeOrigen, String clabeDestino,
                                                BigDecimal monto, BigDecimal saldoOrigenTrasDevolucion, Instant fecha) {
        return new EventoTransferencia(eventoId, REVERTIDA, transferenciaId, clabeOrigen, clabeDestino, monto,
            saldoOrigenTrasDevolucion, null, fecha);
    }

    /** La routing key del contrato. */
    public String routingKey() {
        return REVERTIDA.equals(tipo) ? "transferencia.revertida" : "transferencia.realizada";
    }
}

3.3 · El exchange y el convertidor JSON

Transferencia solo necesita el exchange: publica ahí y no sabe qué colas hay detrás. Las colas son de quien consume. Al conectarse, Spring le pide al broker que exista cada @Bean de tipo exchange. Si ya existe con las mismas propiedades, no pasa nada. Crea mensajeria/ConfiguracionMensajeria.java:

package mx.mexibanco.mensajeria;

import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.amqp.core.ExchangeBuilder;
import org.springframework.amqp.core.TopicExchange;
import org.springframework.amqp.support.converter.Jackson2JsonMessageConverter;
import org.springframework.amqp.support.converter.MessageConverter;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ConfiguracionMensajeria {

    public static final String EXCHANGE = "transferencias";

    /** Topic: el consumidor elige con patrones. Durable: sobrevive a un reinicio del broker. */
    @Bean
    TopicExchange exchangeTransferencias() {
        return ExchangeBuilder.topicExchange(EXCHANGE).durable(true).build();
    }

    /** Los eventos viajan como JSON. Spring Boot se lo pone al RabbitTemplate por ser el único convertidor. */
    @Bean
    MessageConverter convertidorJson(ObjectMapper json) {
        return new Jackson2JsonMessageConverter(json);
    }
}

Se usa el ObjectMapper de Spring Boot, el mismo de las respuestas HTTP, para que fecha salga como texto ISO-8601 y no como número.

3.4 · Que el broker confirme: publisher confirms

Sin confirmación, publicar regresa en cuanto los bytes salen por el socket. Si el broker se cae en ese instante, el evento se pierde y nadie se entera. Con publisher confirms, el broker contesta ack cuando ya guardó el mensaje, o nack si no pudo. Abre transferencia/src/main/resources/application.yml y, en la zona marcada LAB S09, agrega lo verde debajo de rabbitmq::

  rabbitmq:
    host: ${RABBIT_HOST:localhost}
    port: ${RABBIT_PORT:5672}
    username: ${RABBIT_USER:mexibanco}
    password: ${RABBIT_PASSWORD:mexibanco}
    connection-timeout: 2s              # si el broker no contesta, rendirse a los 2 s (60 s por omisión)
    publisher-confirm-type: correlated  # el broker contesta ack o nack por cada mensaje
    publisher-returns: true             # y regresa el que ninguna cola recibió...
    template:
      mandatory: true                   # ...en lugar de tirarlo en silencio

Y, dentro de mexibanco:, cuánto esperar la confirmación:

mexibanco:
  ...
  mensajeria:
    espera-confirmacion-ms: ${ESPERA_CONFIRMACION_MS:5000}

3.5 · El publicador

Esta clase publica un evento y espera la confirmación. La CorrelationData une la confirmación, que llega después por otro hilo, con este mensaje. Primero una excepción de una línea, mensajeria/EventoNoPublicadoException.java:

package mx.mexibanco.mensajeria;

public class EventoNoPublicadoException extends RuntimeException {
    public EventoNoPublicadoException(String mensaje) { super(mensaje); }
    public EventoNoPublicadoException(String mensaje, Throwable causa) { super(mensaje, causa); }
}

Y el publicador, mensajeria/PublicadorDeEventos.java:

package mx.mexibanco.mensajeria;

import org.springframework.amqp.core.MessageDeliveryMode;
import org.springframework.amqp.core.ReturnedMessage;
import org.springframework.amqp.rabbit.connection.CorrelationData;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.util.concurrent.ExecutionException;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.TimeoutException;

@Component
public class PublicadorDeEventos {

    private final RabbitTemplate rabbit;
    private final long esperaConfirmacionMs;

    public PublicadorDeEventos(RabbitTemplate rabbit,
                               @Value("${mexibanco.mensajeria.espera-confirmacion-ms:5000}") long esperaConfirmacionMs) {
        this.rabbit = rabbit;
        this.esperaConfirmacionMs = esperaConfirmacionMs;
    }

    /** Regresa solo si el broker confirmó el evento. Si no, lanza EventoNoPublicadoException. */
    public void publicar(EventoTransferencia evento) {
        String id = evento.eventoId().toString();
        CorrelationData correlacion = new CorrelationData(id);
        try {
            rabbit.convertAndSend(ConfiguracionMensajeria.EXCHANGE, evento.routingKey(), evento, mensaje -> {
                mensaje.getMessageProperties().setDeliveryMode(MessageDeliveryMode.PERSISTENT); // a disco
                mensaje.getMessageProperties().setMessageId(id);   // se ve en el panel sin abrir el JSON
                return mensaje;
            }, correlacion);
        } catch (RuntimeException sinConexion) {
            throw new EventoNoPublicadoException("No se pudo mandar el evento " + id + " al broker: " + sinConexion.getMessage(), sinConexion);
        }
        CorrelationData.Confirm confirmacion;
        try {
            confirmacion = correlacion.getFuture().get(esperaConfirmacionMs, TimeUnit.MILLISECONDS);
        } catch (TimeoutException | ExecutionException sinRespuesta) {
            throw new EventoNoPublicadoException("El broker no confirmo el evento " + id + ": " + sinRespuesta, sinRespuesta);
        } catch (InterruptedException interrumpido) {
            Thread.currentThread().interrupt();
            throw new EventoNoPublicadoException("Se interrumpio la espera del evento " + id, interrumpido);
        }
        if (!confirmacion.isAck()) {
            throw new EventoNoPublicadoException("El broker rechazo el evento " + id + " (nack): " + confirmacion.getReason());
        }
        ReturnedMessage regresado = correlacion.getReturned();   // lo regresó por mandatory
        if (regresado != null) {
            throw new EventoNoPublicadoException("Ninguna cola recibio el evento " + id + " con la routing key "
                + regresado.getRoutingKey() + " (" + regresado.getReplyText() + ")");
        }
    }
}

Tres cosas cuidan el mensaje: la confirmación (el broker dice que lo tiene), mandatory (si ninguna cola lo recibe, el broker lo regresa en vez de confirmarlo y ya) y la entrega persistente (se escribe a disco y sobrevive a un reinicio si la cola es durable).

4Consumir el evento

Minutos 40 a 60 · ahora en el servicio notificacion.

Del otro lado del buzón, notificación necesita tres cosas: su cola enlazada al exchange, un consumidor que lea cada mensaje y guarde los avisos, y una regla: confirmar el mensaje solo después de guardar.

4.1 · La cola y su binding

La cola es de notificación: se llama como su dueño y vive aunque notificación esté apagado. Ahí esperan los eventos. Crea notificacion/src/main/java/mx/mexibanco/notificacion/mensajeria/ConfiguracionMensajeria.java:

package mx.mexibanco.notificacion.mensajeria;

import org.springframework.amqp.core.BindingBuilder;
import org.springframework.amqp.core.Declarables;
import org.springframework.amqp.core.ExchangeBuilder;
import org.springframework.amqp.core.Queue;
import org.springframework.amqp.core.QueueBuilder;
import org.springframework.amqp.core.TopicExchange;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class ConfiguracionMensajeria {

    public static final String EXCHANGE = "transferencias";
    public static final String COLA = "notificacion.transferencias";
    public static final String PATRON = "transferencia.*";

    @Bean
    Declarables topologia() {
        // El mismo exchange que declara transferencia, con las mismas propiedades (topic, durable).
        // Se declara aquí también para poder enlazar la cola aunque notificacion arranque primero.
        TopicExchange transferencias = ExchangeBuilder.topicExchange(EXCHANGE).durable(true).build();
        // Durable: la cola y sus mensajes persistentes sobreviven a un reinicio del broker.
        Queue cola = QueueBuilder.durable(COLA).build();
        return new Declarables(transferencias, cola, BindingBuilder.bind(cola).to(transferencias).with(PATRON));
    }
}
Ojo: esta cola todavía no tiene DLQ En la sección 6 (tarea) le vas a agregar dos argumentos, x-dead-letter-exchange y x-dead-letter-routing-key. RabbitMQ no deja cambiar los argumentos de una cola que ya existe: al arrancar verás PRECONDITION_FAILED. Cuando llegues ahí, tendrás que borrar la cola desde el panel. Hoy déjala así.

4.3 · Guardar los avisos

Por cada TransferenciaRealizada van dos avisos: a quien envió y a quien recibió. Por cada TransferenciaRevertida, uno: a origen, porque su dinero regresó. Abre notificacion/.../NotificacionService.java (tiene un comentario LAB S09) y agrega:

import java.math.BigDecimal;
...
    @Transactional
    public List<Notificacion> avisarDeTransferencia(EventoTransferencia evento) {
        List<Notificacion> avisos = switch (evento.tipo()) {
            case EventoTransferencia.REALIZADA -> List.of(
                aviso(evento.clabeOrigen(), "TRANSFERENCIA_ENVIADA", evento.monto(), evento.saldoOrigen()),
                aviso(evento.clabeDestino(), "TRANSFERENCIA_RECIBIDA", evento.monto(), evento.saldoDestino()));
            case EventoTransferencia.REVERTIDA -> List.of(

            default -> throw new IllegalArgumentException("Tipo de evento desconocido: " + evento.tipo());
        };

    }

    private static Notificacion aviso(String clabe, String tipo, BigDecimal monto, BigDecimal saldo) {
        String mensaje = tipo + " por " + monto.abs() + ", saldo resultante " + saldo;

        return new Notificacion(clabe, mensaje);

4.4 · El consumidor, con ack manual

Cuando RabbitMQ te entrega un mensaje, lo marca Unacked y espera tu respuesta. Si respondes basicAck, lo borra. Si tu proceso muere sin responder, lo vuelve a poner en la cola. Por omisión Spring responde solo, al regresar el método. Lo queremos manual, para decidir nosotros cuándo. En notificacion/src/main/resources/application.yml, en la zona LAB S09:

  rabbitmq:
    ...
    password: ${RABBIT_PASSWORD:mexibanco}
    listener:
      simple:
        acknowledge-mode: manual   # el consumidor dice cuándo (basicAck)
        prefetch: 5                # máximo 5 sin ack a la vez (250 por omisión)

Ahora el consumidor. Abre el esqueleto notificacion/.../mensajeria/ConsumidorDeTransferencias.java y reemplaza la clase vacía. Lee el JSON a mano: así, en la tarea, un mensaje ilegible será un caso más de este método.

package mx.mexibanco.notificacion.mensajeria;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.rabbitmq.client.Channel;
import mx.mexibanco.notificacion.EventoTransferencia;
import mx.mexibanco.notificacion.Notificacion;
import mx.mexibanco.notificacion.NotificacionService;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.amqp.core.Message;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.stereotype.Component;

import java.io.IOException;
import java.util.List;

@Component
public class ConsumidorDeTransferencias {

    private static final Logger log = LoggerFactory.getLogger(ConsumidorDeTransferencias.class);

    private final NotificacionService notificaciones;
    private final ObjectMapper json;

    public ConsumidorDeTransferencias(NotificacionService notificaciones, ObjectMapper json) {
        this.notificaciones = notificaciones;
        this.json = json;
    }

    @RabbitListener(queues = ConfiguracionMensajeria.COLA)
    public void recibir(Message mensaje, Channel canal) throws IOException {
        long etiqueta = mensaje.getMessageProperties().getDeliveryTag();
        boolean reentregado = Boolean.TRUE.equals(mensaje.getMessageProperties().getRedelivered());

        EventoTransferencia evento = json.readValue(mensaje.getBody(), EventoTransferencia.class);
        List<Notificacion> avisos = notificaciones.avisarDeTransferencia(evento);   // aquí hace commit
        log.info("[consumidor] {} de la transferencia {} (evento {}, redelivered={}): {} aviso(s) nuevo(s)",
            evento.tipo(), evento.transferenciaId(), evento.eventoId(), reentregado, avisos.size());

        canal.basicAck(etiqueta, false);   // DESPUÉS de guardar: "ya lo tengo, bórralo"
    }
}

Fíjate en el orden. El ack va después del commit. Si notificación muere entre guardar y el ack, el broker no recibió el ack y vuelve a entregar el mensaje con redelivered=true. No se pierde nada, pero puede llegar dos veces. Ese es el problema de la tarea.

5Tarea · El duplicado

En casa · unos 20 minutos.

Lo que vas a hacer La mensajería entrega al menos una vez (at-least-once). Hoy tu consumidor, si recibe dos veces el mismo evento, guarda dos juegos de avisos. Primero provócalo y muéstralo. Después hazlo idempotente.

5.1 · Provócalo

Elige una de estas dos formas.

Desde el panel. Necesitas un mensaje esperando en la cola, así que apaga notificación y haz una transferencia (queda 1 Ready). Luego:

  1. En Queues and Streams, abre notificacion.transferencias. En Get messages, elige Nack message requeue true y presiona Get Message(s). Ves el mensaje sin consumirlo. Copia su Payload.
  2. En Exchanges, abre transferencias. En Publish message, pon la routing key transferencia.realizada, pega el mismo cuerpo (mismo eventoId) y publícalo. Ahora hay 2 Ready.
  3. Enciende notificación y mira la bandeja.

Al espiar la cola con Get messages, el mensaje original vuelve con redelivered=true. Es normal: el panel lo tomó y lo regresó.

Matando el consumidor. Agrega una pausa configurable entre guardar y hacer el ack (un Thread.sleep con un valor de application.yml, por ejemplo PAUSA_ANTES_DEL_ACK_MS, que también tendrás que pasar en el environment de notificacion en el compose). Levanta notificación con una pausa de 15 s, haz una transferencia y, durante la pausa, mátalo:

PAUSA_ANTES_DEL_ACK_MS=15000 docker compose up --build -d notificacion
# transfiere, y durante los 15 s:
docker compose kill notificacion
docker compose up -d notificacion     # sin la variable: pausa 0
Deberías ver (antes del arreglo)
  • Durante la pausa, la cola tiene 1 Unacked: el mensaje se entregó, los avisos ya están en la base y el broker todavía no lo sabe.
  • Al matarlo, el mensaje regresa a Ready. Al volver, el log dice redelivered=true.
  • La bandeja tiene avisos repetidos: el mismo monto dos veces. Toma captura: es el "antes".

5.2 · Arréglalo

Pista

Guarda el eventoId en una tabla con una restricción UNIQUE (o como llave primaria), en la misma transacción que los avisos. Si ya existía, no guardes nada y confirma el mensaje igual. Algo así, al principio de avisarDeTransferencia:

// dentro del mismo @Transactional que saveAll(avisos)
if (procesados.marcarSiEsNuevo(evento.eventoId(), evento.tipo(), evento.transferenciaId()) == 0) {
    return List.of();   // ya lo habíamos procesado: 0 avisos nuevos, y el consumidor hace ack
}

Tres cosas que pensar:

  • marcarSiEsNuevo puede ser una sola sentencia de Postgres: INSERT ... ON CONFLICT (evento_id) DO NOTHING, que regresa cuántas filas insertó (con @Modifying y @Query(nativeQuery = true)).
  • No lo hagas como "consultar si existe y luego insertar": entre esas dos llamadas otra entrega del mismo mensaje puede colarse.
  • Tampoco atrapes la violación de llave: en Postgres eso deja la transacción abortada.

¿Por qué en la misma transacción? Si algo falla después de la marca, el rollback se lleva marca y avisos juntos, y la siguiente entrega lo intenta desde cero.

Terminado cuandoRepites el experimento y la bandeja tiene un solo juego de avisos. En el log, la segunda entrega dice 0 aviso(s) nuevo(s). Toma captura: es el "después".

7Reto opcional · Outbox

Suma puntos · en casa.

Hasta aquí, notificación puede caerse y nada se pierde. Pero, ¿y si RabbitMQ es el que está caído cuando la saga llega a COMPLETADA?

docker compose stop rabbitmq
curl -i -X POST http://localhost:8080/api/transferencias -H 'Content-Type: application/json' \
  -d '{"claveOrigen":"002180000000000001","claveDestino":"002180000000000002","monto":1}'
docker compose logs transferencia | grep evento
docker compose start rabbitmq

La transferencia responde 201 y queda COMPLETADA (tarda unos 2 s más, por el connection-timeout). Pero el log dice que el evento no se publicó, y al volver el broker nadie lo manda: ese aviso no llega nunca. Es la doble escritura de la clase: la base dice que la transferencia se completó y el evento nunca sale, porque base y broker son dos sistemas sin una transacción que los una.

Tres pistas para un Transactional Outbox
  1. Una tabla outbox en la base de transferencia, escrita en la misma transacción que el cambio de estado final. La saga ya no habla con RabbitMQ: deja el evento en su propia base. Ojo: @Transactional en un método privado, o llamado desde la misma clase, no hace nada; un TransactionTemplate te sirve.
  2. Un relay @Scheduled que cada segundo toma las filas pendientes, las publica con tu PublicadorDeEventos (que espera la confirmación) y las marca como publicadas. Si el broker no confirma, la fila sigue pendiente para la siguiente vuelta. La saga ya usa @Scheduled para el reintento de compensaciones.
  3. SELECT ... FOR UPDATE SKIP LOCKED si corres más de una réplica de transferencia: cada relay se lleva filas distintas en lugar de publicar las mismas dos veces.

Para pensar: si el relay publica y muere antes de marcar la fila, el evento sale otra vez, con el mismo eventoId. ¿Quién te salva de ese duplicado? Y con el broker apagado, ¿transferencia sigue healthy? Revisa qué entra en su /actuator/health.

Terminado cuandoCon RabbitMQ apagado, la transferencia se completa; al encenderlo, el evento sale solo y llega el aviso.
