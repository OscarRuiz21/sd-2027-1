Parte 0 · Lo que un contenedor no resuelve solo

El sábado pasado levantaste nginx, publicaste un puerto y construiste tu imagen. Con eso puedes correr un servicio. Un sistema distribuido son varios, y ahí un contenedor solo deja cuatro huecos:

Hueco del día unoQué pasaLa pieza de hoy

Los cuatro ejercicios de hoy tapan un hueco cada uno, en ese orden. El quinto es diagnóstico. Al final vas a tener un compose.yaml que levanta base de datos, servidor web, caché y broker con docker compose up -d, y ese archivo es lo que entregas.

Ejercicio 1 · Volúmenes: el estado sobrevive al contenedor

Primero, sin volumen: pierde los datos a propósito

Levanta un Postgres, crea una tabla, mete una fila y luego bórralo:

docker run -d --name db1 -e POSTGRES_PASSWORD=secreto postgres:17-alpine
# espera unos 5 segundos: Postgres inicializa su carpeta de datos la primera vez
docker exec -it db1 psql -U postgres -c "CREATE TABLE cuentas(id int primary key, saldo int);"
docker exec -it db1 psql -U postgres -c "INSERT INTO cuentas VALUES (1, 100);"
docker exec -it db1 psql -U postgres -c "SELECT * FROM cuentas;"
Salida esperada de los tres psqlCREATE TABLE INSERT 0 1 id | saldo ----+------- 1 | 100 (1 row)

El exec es el comando cargado de este ejercicio; léelo por partes:

docker exec -it db1 psql -U postgres -c "SELECT * FROM cuentas;" │ │ │ │ │ │ │ └─ el SQL que psql ejecuta y luego sale │ │ └─ el cliente de Postgres, como el usuario postgres │ └─ dentro de cuál contenedor └─ terminal interactiva (en Git Bash de Windows, antepón winpty)

Ahora bórralo a la fuerza y vuelve a crearlo con el mismo comando:

docker rm -f db1
docker run -d --name db1 -e POSTGRES_PASSWORD=secreto postgres:17-alpine
# espera otros 5 segundos
docker exec -it db1 psql -U postgres -c "SELECT * FROM cuentas;"
La tabla ya no existeERROR: relation "cuentas" does not exist LINE 1: SELECT * FROM cuentas; ^

Mismo nombre, misma imagen, misma contraseña, cero datos. Los archivos de la base vivían en la capa de escritura del contenedor, y esa capa se fue con rm. Eso es lo que docker rm -f le hace a una base de datos sin volumen.

Fija el tag: postgres:17-alpine

En Postgres 18 la imagen oficial cambió la ruta de datos (ya no es /var/lib/postgresql/data). Toda esta guía usa 17-alpine; si pones postgres:latest, el volumen se monta en la carpeta equivocada y los datos no persisten. Es la misma lección del sábado pasado: latest no es una garantía, es una etiqueta.

Ahora con un volumen nombrado

docker rm -f db1
docker run -d --name db1 -v datos_banco:/var/lib/postgresql/data -e POSTGRES_PASSWORD=secreto postgres:17-alpine
docker run -d --name db1 -v datos_banco:/var/lib/postgresql/data … postgres:17-alpine │ │ │ │ │ └─ la carpeta DEL CONTENEDOR donde Postgres guarda todo │ └─ el nombre del volumen: Docker lo crea si no existe └─ monta: "lo que el contenedor escriba ahí, guárdalo afuera"

Repite la secuencia completa: crear la tabla, insertar, borrar el contenedor, recrearlo con el mismo -v y consultar:

docker exec -it db1 psql -U postgres -c "CREATE TABLE cuentas(id int primary key, saldo int);"
docker exec -it db1 psql -U postgres -c "INSERT INTO cuentas VALUES (1, 100);"
docker rm -f db1
docker run -d --name db1 -v datos_banco:/var/lib/postgresql/data -e POSTGRES_PASSWORD=secreto postgres:17-alpine
docker exec -it db1 psql -U postgres -c "SELECT * FROM cuentas;"
La fila sobrevivió al contenedor id | saldo ----+------- 1 | 100 (1 row)

El contenedor murió; el volumen no. Míralo:

docker volume ls
docker volume inspect datos_banco
Deberías ver algo asíDRIVER VOLUME NAME local datos_banco [ { "CreatedAt": "2026-09-12T13:05:37Z", "Driver": "local", "Labels": null, "Mountpoint": "/var/lib/docker/volumes/datos_banco/_data", "Name": "datos_banco", "Options": null, "Scope": "local" } ]

Si docker volume ls te escupe cientos de renglones con nombres de 64 caracteres

Son volúmenes anónimos: los crea Docker cuando corres una imagen que declara un volumen y tú no le das -v (justo lo que acabas de hacer con Postgres en el primer intento). Quedan ahí, sin nombre y sin contenedor, con los datos adentro. Para encontrar el tuyo, filtra:

docker volume ls | grep datos_banco

Y ojo con la tentación de "limpiar": docker volume prune borra todos los anónimos que no estén en uso, de todos tus proyectos, sin preguntar cuáles te importaban. En la limpieza del final de esta guía se borra solo lo de hoy, por nombre.

Ese Mountpoint es la carpeta real donde viven los archivos. En Linux la puedes ver con sudo ls; en Mac y Windows está dentro de la máquina virtual de Docker Desktop, y no te hace falta entrar: Docker administra el volumen, tú lo nombras.

Volumen nombrado o bind mount

Hay dos formas de montar. Volumen nombrado (-v datos_banco:/ruta): Docker decide dónde guardarlo, es portable y es lo que usa una base de datos. Bind mount (-v $(pwd)/carpeta:/ruta): montas una carpeta tuya, con ruta absoluta, y ves los archivos desde tu editor: ideal para desarrollo (tu código adentro del contenedor sin reconstruir). En PowerShell de Windows, $(pwd) se escribe ${PWD}; en Codespaces y Linux es tal cual.

Volumen nombradoBind mount
Sintaxis-v nombre:/ruta-v /ruta/absoluta:/ruta
Quién lo administraDockerTú (es tu carpeta)
Para quéDatos de servicios: bases, colas, caché con persistenciaCódigo y archivos que editas mientras el contenedor corre
Sobrevive a docker rmSíSí (nunca fue del contenedor)

La regla que se lleva el día: la imagen es inmutable, el estado vive en el volumen. Si un contenedor guarda algo que te importa y no hay -v, ese algo ya está perdido; solo falta que te enteres.

Ejercicio 2 · Redes: contenedores que se encuentran por nombre

Crea una red y mete un servidor web en ella. Después, desde otro contenedor de la misma red, pídele la página por su nombre:

docker network create redlab
docker run -d --name web --network redlab nginx:alpine
docker run --rm --network redlab alpine:3.20 wget -qO- http://web
Responde el HTML de nginx (recortado)<!DOCTYPE html> <html> <head> <title>Welcome to nginx!</title> …
docker run --rm --network redlab alpine:3.20 wget -qO- http://web │ │ │ │ │ │ │ └─ baja la URL y la imprime (-q calla, -O- a pantalla); │ │ │ "web" es el NOMBRE del otro contenedor │ │ └─ un Linux mínimo, solo para tener wget │ └─ conéctalo a la misma red que "web" └─ bórralo al terminar: es un cliente de un solo uso

No publicaste ningún puerto (no hay -p) y no buscaste ninguna IP: el nombre del contenedor es un nombre DNS dentro de la red. Docker corre un pequeño servidor DNS para cada red que tú creas, y ahí registra a cada contenedor por su --name.

La contraprueba: fuera de la red no hay nombre

docker run --rm alpine:3.20 wget -qO- http://web
Sin --network, fallawget: can't connect to remote host (127.0.53.53): Connection refused

Este contenedor cayó en la red bridge por defecto, y el bridge por defecto no resuelve nombres. Solo las redes definidas por el usuario (las que creas con docker network create, o las que Compose crea por ti) traen DNS. Por eso el sábado pasado dos contenedores no se veían, y por eso hoy sí.

Por qué esa dirección tan rara, y qué ves si no

Sin una red de Docker que conozca a web, la pregunta se fue al DNS de internet, y web es un dominio de primer nivel nuevo: ICANN contesta 127.0.53.53, su dirección de "colisión de nombres", mientras se estrena. Si tu resolver no llega hasta allá, vas a ver en su lugar wget: bad address 'web': las dos salidas dicen lo mismo. Compruébalo con un nombre que no sea dominio de nadie, y sale siempre el clásico:

docker run --rm alpine:3.20 wget -qO- http://db
Ningún DNS conoce a "db"wget: bad address 'db'

El punto no cambia: fuera de la red, web no es tu contenedor.

Mira quién vive en la red y con qué dirección:

docker network inspect redlab
La parte que importa (recortada)"Containers": { "98e7492564c4…": { "Name": "web", "IPv4Address": "172.18.0.2/16", …

La IP existe, pero tú no la usaste y no la vas a usar: si borras web y lo recreas, puede tocarle otra, y el nombre sigue siendo web. Para ver solo nombres y direcciones: docker network inspect redlab --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{println}}{{end}}'.

Eso que acabas de ver es "service discovery", versión mínima

Nombre estable, dirección de hoy. El cliente pregunta por web; alguien (aquí, el DNS de Docker) le contesta la dirección que web tiene ahorita. Cuando el sistema crece a tres máquinas y N réplicas, ese "alguien" se vuelve una pieza con nombre propio, y la teoría de las 08:00 la explica. Tú ya la usaste.

Ejercicio 3 · Variables de entorno: una imagen, dos configuraciones

Ya usaste -e POSTGRES_PASSWORD=… sin pensarlo. Ahora hazlo a propósito: la misma imagen, levantada dos veces con configuración distinta, las dos en la red del ejercicio anterior:

docker run -d --name db_dev --network redlab -e POSTGRES_PASSWORD=dev -e POSTGRES_DB=banco_dev postgres:17-alpine
docker run -d --name db_prod --network redlab -e POSTGRES_PASSWORD=prod -e POSTGRES_DB=banco_prod postgres:17-alpine
docker exec db_dev env | grep POSTGRES
docker exec db_prod env | grep POSTGRES
Cada contenedor ve solo su configuración (las dos líneas pueden salir en otro orden)POSTGRES_PASSWORD=dev POSTGRES_DB=banco_dev POSTGRES_PASSWORD=prod POSTGRES_DB=banco_prod

env imprime las variables de entorno del proceso dentro del contenedor; en tu máquina esas variables no existen. La imagen no cambió: postgres:17-alpine es la misma en los dos. Cambió el gafete. Compruébalo con la base de datos que cada uno creó:

# espera unos 5 segundos: las dos bases se están inicializando
docker exec db_dev psql -U postgres -c "\l" | grep banco
Salida esperada banco_dev | postgres | UTF8 | …

Sacar la configuración a un archivo

Cinco -e en una línea no escalan. Crea en tu carpeta s04 un archivo llamado .env (con punto, sin extensión):

POSTGRES_PASSWORD=secreto
POSTGRES_DB=banco

Y pásalo entero:

docker run --rm --env-file .env postgres:17-alpine env | grep POSTGRES
Las mismas variables, leídas del archivoPOSTGRES_PASSWORD=secreto POSTGRES_DB=banco

Una línea por variable, formato NOMBRE=valor, sin comillas ni espacios alrededor del =. El archivo se busca relativo a donde corres el comando: si docker dice open .env: no such file or directory, estás parado en otra carpeta.

Factor III: la configuración vive fuera de la imagen

The Twelve-Factor App lo dice en una línea: guarda la configuración en el entorno. Configuración es todo lo que cambia entre despliegues (credenciales, direcciones de otros servicios, puertos) y por eso no va dentro de la imagen: la imagen es el uniforme, la configuración es el gafete. El mismo uniforme sirve en desarrollo y en producción; el gafete dice quién eres hoy.

De ahí salen dos reglas de repo que hoy se vuelven obligatorias:

  1. .env NUNCA se sube. Trae contraseñas. Crea un .gitignore en tu carpeta s04 con una sola línea: .env
  2. En su lugar se sube .env.example: los nombres de las variables con valores falsos, para que quien clone sepa qué llenar. Por ejemplo: POSTGRES_PASSWORD=cambia-esto y POSTGRES_DB=banco.

La prueba de fuego del factor III: ¿podrías hacer público tu repo ahora mismo sin comprometer una credencial? Si la respuesta es "mmm", ya sabes qué archivo está mal puesto.

Ejercicio 4 · Compose: el sistema en un archivo

Hasta aquí llevas seis docker run con banderas distintas. Un compañero que quiera reproducir tu sistema tendría que teclearlos igual y en el mismo orden. Compose resuelve eso: describes los servicios en un archivo y Docker los levanta, conecta y apaga juntos. En tu carpeta s04, junto al .env, crea compose.yaml:

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:17-alpine
    env_file: .env
    volumes:
      - datos_banco:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  cache:
    image: redis:8-alpine

  broker:
    image: rabbitmq:4-management-alpine
    ports:
      - "15672:15672"

volumes:
  datos_banco:

Es YAML: la indentación son dos espacios y no hay tabuladores. Cada bloque traduce algo que ya tecleaste hoy:

ClaveQué haceEl equivalente a mano
services:La lista de contenedores del sistema. Cada nombre (web, db…) es un servicio.Un docker run por servicio
image:De qué imagen nace.El último argumento del run
ports:Publica máquina:contenedor. Solo web y la consola de broker se publican; db y cache no, y aun así los demás los alcanzan.-p 8080:80
env_file:Carga las variables desde tu .env.--env-file .env
volumes: (dentro de db)Monta el volumen nombrado en la carpeta de datos.-v datos_banco:/var/lib/postgresql/data
healthcheck:Cómo saber si el servicio ya sirve, no solo si arrancó: pg_isready cada 5 s, hasta 5 intentos.No hay equivalente cómodo: por eso Compose
depends_on: con condition: service_healthyweb no arranca hasta que db pase su healthcheck.Tú esperando 5 segundos con un sleep
volumes: (arriba, al nivel de services)Declara el volumen para que Compose lo cree y lo administre.docker volume create

Lo que no está en el archivo, y no hace falta

No declaraste ninguna red: Compose crea una por proyecto (el proyecto se llama como tu carpeta, así que la red es s04_default) y conecta todos los servicios. Adentro, cada servicio se resuelve por su nombre de servicio: web alcanza a db en db:5432 sin que nadie publique el 5432. Es el ejercicio 2, ya automático. Tampoco hay version: arriba: era de la sintaxis vieja; si lo pones, Compose te avisa que lo ignora. El comando es docker compose, con espacio; el docker-compose con guion es la versión 1, retirada.

Abajo, de tres formas distintas

docker compose stop        # detiene los cuatro; los contenedores siguen ahí
docker compose start       # los revive, con sus datos
docker compose down        # borra contenedores y red; CONSERVA el volumen
docker volume ls           # s04_datos_banco sigue
docker compose up -d       # todo vuelve, y "banco" sigue ahí con lo que tuviera
docker compose down -v     # borra también el volumen: los datos se van
docker volume ls           # s04_datos_banco ya no está
down, y luego down -v Container s04-web-1 Removed Container s04-cache-1 Removed Container s04-broker-1 Removed Container s04-db-1 Removed Network s04_default Removed … Volume s04_datos_banco Removed Network s04_default Removed

Tres niveles de "abajo": stop es pausa, down es "quita el sistema pero guarda el estado", down -v es "borra todo, incluidos los datos". Aprende a distinguirlos hoy; en el reto te van a preguntar exactamente eso.

¿Y en tres máquinas?

Todo lo de hoy vive en una máquina: la tuya. Compose es magnífico para eso y no pretende más. Apenas el sistema necesita dos o tres máquinas, aparecen preguntas que compose.yaml no responde:

  • ¿Quién reinicia un contenedor que muere? restart: unless-stopped lo hace, pero solo en esta máquina; si la máquina se apaga, nadie.
  • ¿Quién reparte los contenedores entre tres máquinas, y los mueve cuando una se llena?
  • ¿Quién da una dirección estable cuando la instancia cambia de máquina y su IP cambia con ella? El DNS de hoy solo conoce esta máquina.
  • ¿Quién guarda el secreto? Tu .env está en tu disco; en tres máquinas hay que repartirlo sin copiarlo a mano.

La respuesta a las cuatro tiene nombre: un orquestador. La lectura de esta semana (Burns et al., Borg, Omega, and Kubernetes) cuenta cómo Google llegó ahí en tres intentos. En la S5 desglosamos el sistema del curso con compose, que es justo lo que ya sabes leer, y cerramos con Kubernetes básico: el mismo compose.yaml, pensado para N máquinas.

No corras docker volume prune para "dejarlo limpio"

Borra de un golpe todos los volúmenes anónimos que no estén en uso en tu máquina, no solo los de hoy, y ahí puede haber datos de otros proyectos tuyos (cualquier base que hayas levantado sin -v dejó uno). No pregunta cuáles. Borra por nombre, como arriba: es más largo y no te lleva nada por delante.

Si algo falla

SíntomaArreglo
port is already allocatedOtro contenedor (quizá tu web del ejercicio 2, o miweb del sábado pasado) tiene el 8080. docker ps para ver quién; bórralo o cambia el puerto del host en ports:.
wget: bad address 'web' estando dentro de la redO el nombre está mal escrito, o ese contenedor no está en esa red: docker network inspect redlab y busca su nombre. Fuera de la red es el comportamiento correcto.
can't connect to remote host (127.0.53.53)Es el bad address con otro disfraz: el nombre lo contestó el DNS de internet, no Docker. Ese contenedor no está en tu red.
password authentication failedEl volumen guardó la contraseña de la primera vez: POSTGRES_PASSWORD solo se aplica cuando la carpeta de datos está vacía. O regresas al valor original en tu .env, o docker compose down -v (pierdes los datos).
env file … .env not found / open .env: no such fileEl .env se busca en la carpeta donde está tu compose.yaml (o donde corres docker run). Párate ahí: ls -a lo muestra.
psql: error: connection … failed justo después del runPostgres todavía está inicializando. Espera 5 segundos y repite, o mira docker logs db1 hasta ver ready to accept connections.
the input device is not a TTY (Git Bash en Windows)Antepón winpty al docker exec -it, o quita -it cuando el comando trae -c y no necesita terminal.
Windows: el bind mount no encuentra la carpetaEn PowerShell es ${PWD}, no $(pwd); en cmd es %cd%. Y Docker Desktop debe tener compartida la unidad donde está tu carpeta.
docker compose: 'compose' is not a docker commandTe falta el plugin: en Linux instala docker-compose-plugin; Docker Desktop lo trae. No instales docker-compose con guion: es la versión 1, retirada en 2023.
the attribute 'version' is obsoleteCopiaste un compose viejo. Borra la línea version:; todo lo demás sigue igual.
Un servicio sale (unhealthy) y up dice dependency failed to startEl healthcheck no pasó: docker compose logs db. Suele ser el .env incompleto (sin POSTGRES_PASSWORD, Postgres se niega a arrancar) o el tag equivocado de la imagen.
network redlab has active endpointsHay contenedores conectados. Bórralos primero (docker rm -f …) y luego docker network rm redlab.
YAML: mapping values are not allowed o "did not find expected key"Indentación. Dos espacios por nivel, nunca tabuladores, y los dos puntos pegados a la clave. docker compose config te dice la línea.
