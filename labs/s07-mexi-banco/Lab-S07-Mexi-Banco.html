1La historia: partimos el banco

Minutos 0 a 15 · se platica en grupo; tú solo lees y miras el código.

Así era: un monolito

Hasta la S05, Mexi Banco era una sola aplicación con una sola base de datos. Una transferencia era una llamada a método: TransferenciaService le pedía a CuentaService que cargara a una cuenta y abonara a la otra. Todo vivía dentro de un @Transactional: si el abono fallaba, la base deshacía también el cargo. O pasaba todo o no pasaba nada.

// 01-monolito · TransferenciaService.java (resumido)
@Transactional
public Transferencia transferir(String origen, String destino, BigDecimal monto) {
    Cuenta o = cuentas.cargar(origen, monto);    // llamada a método, misma base
    Cuenta d = cuentas.abonar(destino, monto);   // si truena aquí, se deshace el cargo
    ...
}

Así quedó: cinco servicios

En la S06 lo partimos en cinco servicios: cuenta, movimiento, transferencia, notificación y SPEI. Cada uno es un programa aparte, en su propio contenedor y con su propia base. El código de transferir casi no cambió, pero cuentas ya no es un objeto en memoria: es un cliente que hace una petición HTTP a otro proceso.

// 02-separacion · TransferenciaService.java (resumido)
public Transferencia transferir(String origen, String destino, BigDecimal monto) {
    CuentaRemota o = cuentas.cargar(origen, monto);   // HTTP: confirmado en cuenta desde aquí
    CuentaRemota d = cuentas.abonar(destino, monto);  // si esto falla, el cargo NO se deshace
    ...
}

2El directorio: que cada servicio se anote solo

Minutos 15 a 35 · aquí empiezas a editar.

Un directorio (service discovery) es una agenda viva: dice qué servicios existen y en qué dirección está cada uno. Funciona así:

  1. Cada servicio, al arrancar, se anota con su nombre (por ejemplo, cuenta) y su dirección IP.
  2. Después manda un heartbeat cada 5 segundos: "sigo vivo".
  3. Si el directorio deja de recibir heartbeats durante un plazo (aquí, 15 s), lo borra de la agenda.
  4. Quien quiera llamar a cuenta le pregunta al directorio y recibe la lista de direcciones vigentes.

Vamos a usar Eureka, el directorio de Spring Cloud. Ya está en la carpeta discovery, pero apagado.

2.0 · Antes de tocar nada: ¿cómo está hoy?

Levanta el proyecto tal como lo construiste en casa (tarda menos de un minuto):

docker compose up -d     # levanta lo que ya está construido
docker compose ps        # seis contenedores: la base y los cinco servicios, cada uno con su puerto

En la columna PORTS verás que cada servicio tiene su propia puerta en tu laptop: cuenta en 8081, movimiento en 8082, transferencia en 8083, notificación en 8084 y SPEI en 8085. Ahora abre en tu navegador:

  • http://localhost:8081/cuentas/000 → cuenta te contesta directo: "no existe la cuenta 000" (un 404 en JSON).
  • http://localhost:8761 → no carga. Todavía no hay directorio.

Guarda esa imagen mental. Al final de este paso, la segunda liga va a mostrar a los cinco servicios.

2.1 · Convierte la aplicación en directorio

La carpeta discovery es una aplicación de Spring Boot que ya trae la librería del servidor Eureka, pero nadie le dijo que la usara. La anotación @EnableEurekaServer la enciende. Abre discovery/src/main/java/mx/mexibanco/DiscoveryApplication.java y agrega lo que está en verde:

import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.netflix.eureka.server.EnableEurekaServer;

@SpringBootApplication
@EnableEurekaServer
public class DiscoveryApplication {

2.2 · Que el directorio no se anote a sí mismo

Un servidor Eureka también trae el cliente. Por eso, sin más, intentaría anotarse en "otro" directorio, que sería él mismo. Como es el único, le decimos que no se registre y que no pida la lista a nadie. Abre discovery/src/main/resources/application.yml y, debajo de client:, agrega las dos líneas en verde:

eureka:
  client:
    register-with-eureka: false
    fetch-registry: false
  server:

Si tuviéramos varios directorios para no depender de uno solo, sí se registrarían entre ellos. Hoy basta uno.

2.3 · Enséñale a cada servicio a anotarse

Ahora el otro lado: cada servicio necesita el cliente de Eureka, la librería que al arrancar lo anota y luego manda los heartbeats. Ya está escrita en cada pom.xml, pero comentada. Abre cada uno de estos archivos: cuenta/pom.xml, movimiento/pom.xml, transferencia/pom.xml, notificacion/pom.xml y spei/pom.xml. Busca el bloque marcado con TODO H1 y borra solo las dos líneas que abren y cierran el comentario (<!-- y -->), para que quede así:

<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-netflix-eureka-client</artifactId>
</dependency>

¿Y cómo sabe cada servicio con qué nombre anotarse y dónde está el directorio? Eso ya estaba listo:

  • El nombre sale de spring.application.name en el application.yml de cada servicio (por ejemplo, name: cuenta).
  • La dirección del directorio y los tiempos están arriba del docker-compose.yml, en x-directorio: EUREKA_URL (dónde está), EUREKA_LATIDO_S: 5 (heartbeat cada 5 s) y EUREKA_EXPIRA_S: 15 (plazo de 15 s). Spring trae 30 y 90 segundos; los bajamos para que en clase todo se vea rápido.

2.4 · Enciende el directorio en Docker

Falta decirle a Docker que levante el directorio. En docker-compose.yml hay dos pedazos comentados con TODO H1:

  1. El servicio discovery: completo. Selecciona sus líneas y quítales el # (en IntelliJ y VS Code: ⌘/ en Mac, Ctrl+/ en Windows). Fíjate que publica el puerto 8761: es el de la liga que hace rato no cargaba.
  2. Arriba, en depends_on, las dos líneas discovery: y condition: service_healthy. Así los cinco servicios esperan a que el directorio esté sano antes de arrancar y se anotan al primer intento.

Construye y levanta. Como cambiaste los cinco pom.xml, Docker vuelve a compilar los cinco servicios: tarda unos 9 minutos. Mientras, platicamos qué pasa si un servicio deja de mandar heartbeats.

docker compose up -d --build     # reconstruye lo que cambió y levanta todo
docker compose ps                # espera siete "healthy": la base, los cinco y el directorio

2.5 · Compruébalo en el navegador

Abre otra vez http://localhost:8761. Ahora sí carga: es el tablero de Eureka.

Deberías ver
  • En Instances currently registered with Eureka, cinco renglones: CUENTA, MOVIMIENTO, NOTIFICACION, SPEI y TRANSFERENCIA. Cada uno dice UP (1): una copia viva.
  • Junto a cada nombre, el identificador de la instancia, algo como 6bd55a1c1cd7:cuenta:8080. El primer pedazo es el ID del contenedor (compáralo con docker ps).
  • Un letrero rojo, "THE SELF PRESERVATION MODE IS TURNED OFF". Es normal: lo apagamos a propósito para que Eureka borre rápido a los que dejan de mandar heartbeats.
Toma captura para tu bitácora.

El tablero es para humanos. Los servicios le preguntan lo mismo al directorio por una API. Ábrela tú también en el navegador: http://localhost:8761/eureka/apps/CUENTA. Es un XML con lo que el directorio sabe de cuenta:

  • <hostName>: la IP del contenedor dentro de la red de Docker.
  • <port>: 8080.
  • <status>: UP.
  • <renewalIntervalInSecs>5 y <durationInSecs>15: el heartbeat y el plazo del compose.
Experimento corto (opcional) Apaga un servicio y míralo desaparecer del tablero. Recarga localhost:8761 cada pocos segundos: 
docker compose stop notificacion     # apaga notificación
docker compose start notificacion    # y lo vuelve a prender
En el ensayo tardó unos 18 segundos en desaparecer y unos 9 en volver. ¿Por qué no desaparece al instante? Pista: el plazo.
Piensa Los cinco ya están anotados. Pero en el compose, transferencia sigue llamando a CUENTA_URL: http://cuenta:8080, una dirección escrita a mano. ¿Alguien está usando el directorio para encontrar a cuenta? Anota tu respuesta: la retomamos en el paso 4.

3El gateway: una sola puerta

Minutos 35 a 50

Hoy cada servicio tiene su propia puerta hacia afuera, y eso trae dos problemas:

  • El cliente (una app, una página web) tiene que conocer cinco direcciones.
  • Cualquiera puede llamar a operaciones que deberían ser internas.

Compruébalo. Registrar un movimiento es algo que solo hacen los servicios entre ellos, y aun así:

curl -i -X POST http://localhost:8082/movimientos    # llamada directa a movimiento, desde tu laptop

Responde 400 ("te faltan datos"), no 404: el endpoint existe y está abierto a cualquiera. curl -i hace una petición, como el navegador, y te muestra el código de respuesta y las cabeceras.

Un API gateway resuelve los dos problemas. Es la única entrada para los clientes, en el puerto 8080. Según la ruta de cada petición, decide a qué servicio mandarla. Lo que no tenga regla no pasa.

Antes (hoy)Después de este paso
Consultar una cuentalocalhost:8081/cuentas/123localhost:8080/api/cuentas/123
Consultar movimientoslocalhost:8082/movimientoslocalhost:8080/api/movimientos
Registrar un movimiento (interno)Abierto en el 8082El gateway contesta 404: no hay ruta

3.1 · Escribe las rutas

Abre gateway/src/main/resources/application.yml. Ya existe la ruta de cuenta, como ejemplo. Cada ruta dice tres cosas:

  • Cuándo aplica (predicates): Path es la ruta que llega y Method el verbo HTTP permitido.
  • A dónde va (uri): lb://cuenta significa "pregúntale al directorio dónde está cuenta y, si hay varias copias, reparte". Aquí el gateway sí usa el directorio.
  • Qué le cambia (filters): StripPrefix=1 quita el primer pedazo de la ruta. /api/cuentas/123 le llega a cuenta como /cuentas/123, que es lo que cuenta sabe atender.

Debajo de la ruta de cuenta, en lugar del comentario TODO H2, pega las otras cuatro. Fíjate en los Method:

  • Movimiento y notificación solo aceptan GET: el cliente consulta, pero no registra.
  • SPEI solo acepta POST.
      routes:
        - id: cuenta
          ...                          # la que ya estaba
        - id: movimiento
          uri: lb://movimiento
          predicates:
            - Path=/api/movimientos
            - Method=GET
          filters:
            - StripPrefix=1
        - id: transferencia
          uri: lb://transferencia
          predicates:
            - Path=/api/transferencias,/api/transferencias/{id}
          filters:
            - StripPrefix=1
        - id: notificacion
          uri: lb://notificacion
          predicates:
            - Path=/api/notificaciones
            - Method=GET
          filters:
            - StripPrefix=1
        - id: spei
          uri: lb://spei
          predicates:
            - Path=/api/spei
            - Method=POST
          filters:
            - StripPrefix=1

Cuida la sangría: cada - id: va alineado con el de cuenta. En YAML, un espacio de más o de menos cambia el significado.

3.2 · Enciende el gateway

En docker-compose.yml, quítale el # al servicio gateway: completo (TODO H2). Mira lo que dice:

  • Publica el 8080: la puerta única.
  • Recibe las variables del directorio, porque también es cliente de Eureka: para resolver lb://cuenta necesita preguntar.
  • Espera a que discovery esté sano.
docker compose up -d --build gateway    # construye y levanta solo el gateway (~1 min)

Recarga localhost:8761: ahora hay un sexto renglón, GATEWAY. El gateway también se anota.

3.3 · Pruébalo

Mexi Banco agrega a cada respuesta de cuenta la cabecera X-Instancia, que dice qué contenedor de cuenta contestó. Nos sirve para saber quién respondió: cuenta o el gateway.

# a) Pedir una cuenta que no existe, entrando por el gateway
curl -i http://localhost:8080/api/cuentas/000

# b) Intentar registrar un movimiento desde afuera, ahora por la puerta
curl -i -X POST http://localhost:8080/api/movimientos
Deberías ver Los dos dan 404, pero por razones distintas:
  • (a) trae X-Instancia: el gateway encontró la ruta, le preguntó al directorio, la petición llegó a cuenta y cuenta dijo "no existe esa cuenta".
  • (b) no trae X-Instancia: el gateway la paró porque ninguna ruta acepta un POST a movimientos. Compáralo con el 400 que te dio el 8082 hace rato: la operación interna ya no se alcanza por la puerta.

Ahora crea tu propia cuenta por el gateway. La primera línea inventa una CLABE única con la hora, para que no choque con la de otra persona:

LAB_CLABE="S07$(date +%s)"
curl -i -X POST http://localhost:8080/api/cuentas \
  -H 'Content-Type: application/json' \
  -d "{\"clabe\":\"$LAB_CLABE\",\"titular\":\"S07\",\"saldoInicial\":0}"

URL="http://localhost:8080/api/cuentas/$LAB_CLABE"   # guardamos la dirección de tu cuenta
curl -i "$URL"
echo "$URL"                                          # imprime la liga para abrirla en el navegador
Deberías verEl alta da 201 y la consulta 200, con saldo 0. Copia la liga que imprimió echo y ábrela en el navegador: verás tu cuenta en JSON, servida por el gateway. No cierres esta terminal: $URL la usamos en los pasos 4 y 5.

4Tres copias de cuenta

Minutos 50 a 62

Supón que cuenta es el servicio más usado y una sola copia no aguanta. La solución es escalar horizontalmente: levantar varias copias idénticas y repartir las peticiones entre ellas. Eso es el balanceo de carga.

Aquí se juntan las tres piezas. Las copias se anotan en el directorio, el gateway pregunta por cuenta y recibe tres direcciones, y el balanceador del gateway reparte por turnos entre ellas.

4.1 · Pide tres copias

En docker-compose.yml, en el servicio cuenta, cambia las dos líneas de ports por deploy (TODO H3):

# antes: una copia, publicada en el 8081
    ports:
      - "8081:8080"
# después: tres copias, sin puerto publicado
    deploy:
      replicas: 3

¿Por qué quitar el puerto? Tres contenedores no pueden ocupar el mismo 8081 de tu laptop, y ya no hace falta: desde afuera se entra por el gateway. Por dentro, cada copia sigue escuchando en su 8080, cada una con su propia IP. Por la misma razón, borra también los ports de movimiento, transferencia, notificación y SPEI. Solo el gateway (8080) y el directorio (8761) quedan publicados.

docker compose up -d     # aplica el cambio: crea las tres copias
docker ps --filter name=cuenta --format '{{.ID}}  {{.Names}}  {{.Ports}}'   # las tres copias, su ID y sus puertos
Deberías ver
  • En la terminal, tres contenedores: mexi-banco-v06-cuenta-1, -2 y -3, cada uno con su ID y con 8080/tcp sin flecha. Escuchan por dentro, pero no están publicados en tu laptop. Anota los tres ID.
  • En localhost:8761, CUENTA dice UP (3), con tres identificadores que empiezan con esos mismos ID. Si un rato ves cuatro, espera unos segundos: la copia vieja aún no vence su plazo.
Ten presente que nadie le avisó al gateway que ahora hay tres copias. Lo sabe porque las tres se anotaron en el directorio.

4.2 · Mira cómo reparte

Este ciclo consulta tu cuenta nueve veces y muestra solo la cabecera que dice qué copia contestó:

for i in {1..9}; do
  curl -sS -D - -o /dev/null "$URL" | grep -i '^X-Instancia'
done
Deberías verTres valores distintos de X-Instancia que se turnan: A, B, C, A, B, C… Son los mismos ID que anotaste. Este reparto por turnos se llama round robin.

Otra forma de verlo, desde el lado de cuenta. En otra terminal deja corriendo los logs de las tres copias y vuelve a lanzar el ciclo en la primera:

docker compose logs -f cuenta | grep atendida    # Ctrl+C para salir

Cada línea empieza con cuenta-1, cuenta-2 o cuenta-3 y dice "GET /cuentas/… atendida por …": las tres copias van atendiendo una por una.

PiensaEsto prueba que el gateway reparte. ¿Y cuando transferencia llama a cuenta por dentro, también reparte? Mira otra vez su CUENTA_URL en el compose. Lo arreglas en la tarea.

5¿Y si una copia se muere?

Minutos 62 a 78

En un sistema distribuido las cosas fallan: un servidor se apaga, la red se corta. Vamos a matar una copia de cuenta sin avisarle a nadie, como si se fuera la luz de ese servidor, y a medir cuánto tarda el sistema en darse cuenta.

Ojo con la diferencia. En el experimento del paso 2 usaste stop, que apaga el servicio con calma. Aquí usamos kill, que lo corta de golpe. En los dos casos el directorio solo se entera porque dejan de llegar los heartbeats.

Antes de correrlo, predice y anótalo¿Van a fallar todas las consultas, ninguna o algunas? ¿Durante cuánto tiempo? ¿Dejan de fallar en cuanto la copia desaparece del directorio, o antes, o después?

Usa dos terminales. En la terminal 1 (donde tienes $URL), deja corriendo una consulta por segundo. Cada línea muestra la hora y el código de respuesta:

for i in {1..60}; do
  echo "$(date +%T)  $(curl -s -o /dev/null -w '%{http_code}' --max-time 3 "$URL")"
  sleep 1
done

En la terminal 2, mata una de las copias:

date +%T                              # anota la hora del apagado
docker kill mexi-banco-v06-cuenta-1   # la apaga de golpe, sin despedirse

Mientras tanto, recarga localhost:8761 cada pocos segundos y anota a qué hora CUENTA pasa de UP (3) a UP (2).

Deberías ver
  • Casi todas las respuestas son 200.
  • Al principio salen algunos errores 500 o 503, salteados: son las peticiones a las que, por turno, les tocó la copia muerta (una de cada tres). Durante unos 20 a 30 segundos aparecen y luego dejan de salir.
  • En el ensayo del profesor hubo 7 errores en 45 consultas, y la copia salió del directorio a los ~33 segundos.

¿Por qué tantos segundos? Porque nadie avisa. El sistema se va enterando por capas:

QuiénCómo se enteraTiempo en el lab
El directorioDeja de recibir heartbeats y espera el plazo para no borrar a alguien que solo se tardó.15 s de plazo, más su revisión periódica (cada 5 s)
El gatewayNo ve el directorio en vivo: guarda una copia de la lista y la renueva con un refresh periódico.Refresh cada 5 s, más 5 s de caché del balanceador
ResultadoMientras tanto, el gateway le sigue mandando peticiones a una copia muerta.Unos 30 s de errores intermitentes

Con los valores de fábrica de Spring (heartbeat 30 s, plazo 90 s) serían minutos. Bajar los tiempos detecta antes, pero carga más al directorio con heartbeats.

Revive la copia y mira cómo vuelve a UP (3) en el tablero:

docker start mexi-banco-v06-cuenta-1

TTarea: que transferencia también reparta

20 a 30 minutos, en casa

Hoy solo reparte el gateway. Por dentro, transferencia sigue llamando a http://cuenta:8080. Ese nombre lo resuelve el DNS de Docker, no el directorio: transferencia no sabe cuántas copias hay ni cuáles están vivas. Vamos a hacer que le pregunte al directorio por el nombre cuenta y reparta ella misma entre las tres copias, igual que el gateway.

T.1 · Un cliente HTTP que sabe preguntar al directorio

Abre transferencia/src/main/java/mx/mexibanco/clientes/ClientesHttp.java. Agrega estos dos imports arriba, con los demás:

import org.springframework.boot.autoconfigure.web.client.RestClientBuilderConfigurer;
import org.springframework.cloud.client.loadbalancer.LoadBalanced;

Y en el lugar del comentario TODO H3, este método. La anotación @LoadBalanced hace la magia: cuando la URL diga http://cuenta, en cada petición cambia "cuenta" por la dirección de una de sus copias registradas.

@Bean
@LoadBalanced
RestClient.Builder restClientBalanceado(RestClientBuilderConfigurer configurador) {
    return configurador.configure(RestClient.builder());
}

T.2 · Llamar por nombre, sin puerto

En docker-compose.yml, dentro de transferencia → environment, cambia las tres URLs:

      CUENTA_URL: http://cuenta
      MOVIMIENTO_URL: http://movimiento
      NOTIFICACION_URL: http://notificacion
