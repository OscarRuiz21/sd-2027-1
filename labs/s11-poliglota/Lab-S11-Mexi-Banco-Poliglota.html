¿Usas Windows? Usa Git Bash, no PowerShell

Todos los comandos de esta guía son de bash, la terminal de Mac y Linux. En Windows, córrelos en Git Bash, que se instaló junto con Git (búscalo en el menú Inicio). En PowerShell y en CMD no funcionan: ahí curl es otro comando, las comillas del JSON se rompen y no existen grep, awk ni seq.

Por eso todos los docker compose exec de la guía llevan -T: le dice a Docker que no abra una terminal interactiva. En Mac y Linux da igual; en Git Bash evita el error the input device is not a TTY.

1Por qué: ninguna base sirve para todo

Minutos 0 a 10 · se platica en grupo; tú solo lees.

Cómo está hoy Mexi Banco

Después de la S09, todo vive en PostgreSQL: las cuentas, los movimientos, las transferencias, el outbox y también los avisos que manda notificación. Funciona, pero hay dos datos a los que Postgres no les queda bien:

  1. El saldo que el cliente consulta. La app lo pide cada vez que alguien abre la pantalla: muchas más veces de las que cambia. Cada consulta es una lectura a Postgres, la misma base que tiene que aguantar los cargos y los abonos.
  2. Los avisos. Un SMS lleva teléfono y texto, un correo lleva dirección, asunto y cuerpo, un push lleva el token del celular. En una tabla eso es una columna por campo de cualquier canal, casi todas vacías, o una tabla por canal. Y nunca se actualizan: se escriben una vez y se leen enteros.

Verdad contra copia

La pregunta del día no es "¿SQL o NoSQL?", sino qué dato es la verdad y qué dato es una copia. La verdad tiene que estar en un lugar que no la pierda ni la contradiga. Una copia se puede reconstruir, y por eso se vale guardarla en otro motor, con otra forma y hasta un poco atrasada.

Las tres reglas de hoy
  1. Nada que sea dinero cambia de motor. Saldo, movimientos y transferencias se quedan en Postgres.
  2. La caché muestra, nunca decide. El cargo que revisa si alcanza el saldo lee Postgres, siempre.
  3. No escribas lo mismo en dos bases. Sin una transacción común, tarde o temprano una se queda sin el dato. Es el problema que vimos en la S09.

4La caché del saldo en Redis

Minutos 15 a 40 · Parte 1 · guiada, en el servicio cuenta.

La idea: cache-aside

Vas a usar el patrón más común, cache-aside: la app pregunta primero a la caché y, si no está, va a la base y deja una copia para la próxima vez.

GET /cuentas/{clabe}
→GET cuentas::{clabe}
Redis
Hit: estaba en RedisContesta Redis. El método ni corre y Postgres ni se entera.
Miss: no estabaCorre el método, lee Postgres y Spring guarda la copia con SET ... PX 30000 (vive 30 s).

Y cuando el saldo cambia (un cargo o un abono), la copia se borra con DEL. No se actualiza: se borra, y la siguiente consulta la vuelve a llenar con el saldo nuevo.

cargar · abonar
→UPDATE
PostgreSQL
→COMMIT, y después
DEL cuentas::{clabe}

El orden importa: primero el commit, después el borrado. Lo vemos en la pregunta 4 del cierre.

En Spring no escribes los GET, SET y DEL a mano: los hacen dos anotaciones. @Cacheable en el método que lee y @CacheEvict en los que cambian el saldo.

4.1 · Enciende y configura la caché

cuenta/src/main/java/mx/mexibanco/cuenta/ConfiguracionCache.java

Qué hace este archivo: Spring Boot ya arma solo un RedisCacheManager, porque el pom.xml trae spring-boot-starter-data-redis. Aquí solo lo enciendes y le cambias tres cosas a la caché cuentas.

Qué cambias: agrega @EnableCaching arriba de la clase y el @Bean de abajo. Lo verde es lo nuevo.

import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.autoconfigure.cache.RedisCacheManagerBuilderCustomizer;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.serializer.Jackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.RedisSerializationContext.SerializationPair;

import java.time.Duration;

// sin @EnableCaching, @Cacheable y @CacheEvict se ignoran sin avisar
@EnableCaching
@Configuration
public class ConfiguracionCache {

    public static final String CUENTAS = "cuentas";

    @Bean
    RedisCacheManagerBuilderCustomizer cacheDeCuentas(
            @Value("${mexibanco.cache.ttl:30s}") Duration ttl, ObjectMapper json) {
        RedisCacheConfiguration cuentas = RedisCacheConfiguration.defaultCacheConfig()
            // 1. cada entrada vive 30 s y luego Redis la borra sola
            .entryTtl(ttl)
            .disableCachingNullValues()
            // 2. el valor se guarda como JSON de CuentaVista, legible con redis-cli
            .serializeValuesWith(SerializationPair.fromSerializer(
                new Jackson2JsonRedisSerializer<>(json, CuentaVista.class)));
        return builder -> builder.withCacheConfiguration(CUENTAS, cuentas)
            // 3. el DEL de @CacheEvict espera al commit de la transacción
            .transactionAware();
    }
}
LíneaPor qué
entryTtl(ttl)Sin TTL, una entrada en Redis no caduca nunca. Si alguien cambia el saldo por fuera de la app (la Parte 4), el dato viejo se quedaría para siempre.
Jackson2JsonRedisSerializerPor omisión Spring guarda el objeto con la serialización binaria de Java (\xac\xed...). En JSON lo puedes leer con redis-cli GET.
transactionAware()El DEL de @CacheEvict espera a que la transacción haga commit. Si borrara antes, otra consulta podría leer el saldo viejo en esa ventana y volver a dejarlo en la caché.

4.2 · Cachea la consulta que muestra

cuenta/src/main/java/mx/mexibanco/cuenta/ConsultaDeSaldo.java

Qué hace este archivo: contesta GET /cuentas/{clabe}, lo que ve el cliente en la app. Cada vez que corre, escribe en el log [consulta] ... leida de Postgres.

Qué cambias: una anotación arriba de consultar. La key dice con qué se arma la clave en Redis: #clabe es el parámetro, y la clave queda cuentas::002180000000000001.

import org.springframework.cache.annotation.Cacheable;
...
    @Cacheable(cacheNames = ConfiguracionCache.CUENTAS, key = "#clabe")
    public CuentaVista consultar(String clabe) {
        log.info("[consulta] {} leida de Postgres", clabe);   // en un hit, esta línea ya no sale
        return cuentas.findByClabe(clabe)
            .map(CuentaVista::de)

    }

4.3 · Borra la copia cuando cambia el saldo

cuenta/src/main/java/mx/mexibanco/cuenta/CuentaService.java

Qué hace este archivo: las reglas de la cuenta. cargar revisa que alcance el saldo y lo resta; abonar lo suma. Los dos los llama la saga de transferencia por HTTP.

Qué cambias: la misma anotación arriba de cargar y de abonar, junto al @Transactional que ya tienen.

import org.springframework.cache.annotation.CacheEvict;
...
    @CacheEvict(cacheNames = ConfiguracionCache.CUENTAS, key = "#clabe")
    @Transactional
    public SaldoAplicado cargar(String clabe, BigDecimal monto, String clave) { ... }

    @CacheEvict(cacheNames = ConfiguracionCache.CUENTAS, key = "#clabe")
    @Transactional
    public SaldoAplicado abonar(String clabe, BigDecimal monto, String clave) { ... }
Lo que NO tocas: CuentaService.consultar

En el mismo archivo hay otro consultar. Es la lectura que usa cargar para decidir si alcanza el saldo, y siempre va a Postgres. Si la cachearas, un cargo podría aprobarse con un saldo de hace 30 s.

Por eso la consulta que muestra vive en otra clase, ConsultaDeSaldo. Hay una segunda razón: si pones @Cacheable en un método y lo llamas desde su misma clase, la llamada no pasa por el proxy de Spring y la anotación se ignora sin avisar.

4.6 · Mide: ¿qué compraste con la caché?

Hit ratio. Redis cuenta sus aciertos (keyspace_hits) y sus fallos (keyspace_misses). El hit ratio es hits / (hits + misses).

# Pone en cero los contadores de Redis
docker compose exec -T redis redis-cli CONFIG RESETSTAT
# Escenario A: cien consultas seguidas del saldo de Ana (-o /dev/null tira la respuesta)
for i in $(seq 1 100); do
  curl -s -o /dev/null http://localhost:8080/api/cuentas/002180000000000001
done
# Muestra los contadores
docker compose exec -T redis redis-cli INFO stats | grep keyspace

Escenario B: lo mismo, pero con una transferencia de 1 peso de Ana a Beto cada diez consultas. Explica por qué baja. Ojo: tus propios redis-cli GET también cuentan.

Lo que dio en la prueba del profeA: 99 hits y 1 miss, 99 %. B: 101 hits y 19 misses, 84 %. Cada transferencia borra a Ana y a Beto, y la siguiente lectura de cada uno falla.

Latencia. Este comando hace 100 consultas, guarda el tiempo de cada una y calcula promedio, mediana y p95 en milisegundos:

# -w '%{time_total}' imprime cuántos segundos tardó cada consulta
for i in $(seq 1 100); do
  curl -s -o /dev/null -w '%{time_total}\n' http://localhost:8080/api/cuentas/002180000000000001
done \
# sort los ordena; awk los pasa a ms y saca promedio, mediana (el de en medio) y p95
  | sort -n \
  | awk '{t[NR]=$1*1000; s+=$1*1000}
         END {printf "promedio=%.2f ms mediana=%.2f ms p95=%.2f ms\n", s/NR, t[int(NR*0.5)], t[int(NR*0.95)]}'

Para medir sin caché no tocas código: application.yml ya lee la variable CACHE_TIPO.

# Reinicia cuenta con la caché apagada; espera a que esté healthy con docker compose ps
CACHE_TIPO=none docker compose up -d cuenta
# ... mide igual, y cuenta también las lecturas a Postgres ...
# Regresa cuenta con la caché encendida
docker compose up -d cuenta
Predice: ¿cuánto más rápida será la consulta con caché?
Ver lo que pasó en la prueba

Casi nada: mediana de 4 a 5 ms con caché y de 5 a 6 ms sin ella. En tu laptop Postgres tiene la tabla en memoria y está a un salto de red, igual que Redis. Lo que sí cambia es cuántas lecturas recibe Postgres: con caché, 200 consultas dentro del TTL dieron 0; sin caché, 200. La caché compra capacidad más que velocidad: Postgres queda libre para los cargos y abonos.

5.2 · registrar(evento): guarda sin duplicar

Qué hace: por cada destinatario arma su documento y lo inserta. Regresa cuántos eran nuevos. Si Mongo contesta que el _id ya existe (DuplicateKeyException), ese aviso ya estaba: no es un error, no se cuenta y se sigue con el siguiente.

public int registrar(EventoTransferencia evento) {
    int nuevos = 0;
    for (Destinatario destinatario : destinatarios(evento)) {
        Document aviso = documento(evento, destinatario, contactos.de(destinatario.clabe()));
        try {
            mongo.insert(aviso, COLECCION);
            nuevos++;
        } catch (DuplicateKeyException yaEstaba) {
            log.info("[avisos] {} ya estaba: evento repetido, no se duplica", aviso.get("_id"));
        }
    }
    return nuevos;
}

¿Por qué uno por uno y no todos juntos? Un insert de varios se detiene en el primer _id repetido. Si el proceso se cayó después de guardar el primer aviso, la reentrega tiene que poder guardar el segundo.

public List<Document> ultimos(String clabe) {
    Query consulta = Query.query(Criteria.where("clabe").is(clabe))
