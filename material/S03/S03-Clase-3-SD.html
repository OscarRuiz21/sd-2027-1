Del monolito al

El modelo cliente-servidor — y los cinco problemas que aparecen al partir un monolito.

Arquitectura · el modelo del que todo parte

Cliente-servidor · roles asimétricos: uno espera, el otro inicia

Definición

Dos roles asimétricos sobre una red: el servidor ofrece un servicio y espera peticiones en una dirección conocida (IP y puerto); el cliente inicia la conversación. Todo lo que sigue en el curso — REST, gRPC, mensajería — es una variación de este modelo.

Las capas
  • 2 capas: interfaz en el cliente ↔ lógica y datos en el servidor.
  • 3 capas: presentación · lógica de negocio · datos. El monolito clásico: las tres en un solo proceso.
  • N capas: la lógica se reparte entre varios servidores — el paso natural hacia los servicios.
  • En microservicios cada servicio juega ambos roles: servidor de su API y cliente de las demás.
Cómo funciona
  1. El servidor arranca y escucha en una dirección conocida: IP:puerto.
  2. El cliente resuelve el nombre a esa dirección: DNS, el naming de Internet (nombre → IP).
  3. Con la IP en mano, abre conexión y envía la petición.
  4. Para responder, el servidor puede actuar a su vez como cliente de otro.
  5. La respuesta regresa; el servidor queda esperando la siguiente petición.
  6. Muchos clientes concurrentes, un servidor: la concurrencia se resuelve del lado del servidor.

Del monolito a los servicios · por qué existen las piezas

Partir el monolito crea problemas nuevos · y cada problema tiene una pieza estándar

Comunicación · qué resuelve cualquier llamada remota

Los componentes de la comunicación · cinco preguntas, siempre las mismas

La idea

Para que un proceso invoque a otro a través de la red, cinco cosas deben quedar resueltas. Cada tecnología del curso es una combinación concreta de respuestas a estas cinco preguntas.

ComponentePregunta que resuelveEn este curso
Naming¿Cómo se llama el destino? Un nombre lógico, no una dirección física.DNS (los nombres de Internet — AWS: Route 53) · nombres de servicio (pagos)
Binding¿Cómo se asocia ese nombre a una dirección concreta (IP:puerto) al momento de llamar?estático (en la config) · dinámico (service discovery, en cada llamada)
Protocolo¿Cómo viajan los bytes, con qué reglas y en qué orden?HTTP sobre TCP · HTTP/2 (gRPC) · AMQP (broker)

Comunicación · la unidad básica: una llamada HTTP

REST · petición y respuesta sobre HTTP

DEFINICIÓN

Estilo de comunicación sobre HTTP (el mismo protocolo que ya conocen de redes): un servicio expone sus datos como recursos con URL propia; otro servicio — o un navegador — los pide y espera la respuesta. Es síncrono: quien llama, espera.

PROBLEMA / CONTEXTO
  • Toda pieza de las próximas slides existe alrededor de estas llamadas.
  • La representación viaja en JSON: texto estructurado de pares campo: valor, legible por humanos y por máquinas.
  • El cliente queda esperando: si el servidor tarda o muere, el cliente lo sufre — de ahí saldrán varias piezas.
CÓMO FUNCIONA
  1. El cliente arma la petición: verbo + ruta del recurso.
  2. La petición viaja por la red al servidor.
  3. El servidor la procesa y arma la respuesta: código de estado + cuerpo.
  4. La respuesta regresa; el cliente la interpreta.
Servicio A (cliente)
Servicio B (servidor)
GET /api/cuentas/42 200 OK + JSON

Anatomía · problema 1: por dónde entra el cliente

API Gateway · punto de entrada único

DEFINICIÓN

Servicio que recibe todas las peticiones externas y las enruta al servicio interno correspondiente, aplicando en un solo lugar las políticas comunes: identidad, cifrado y límites de uso.

PROBLEMA QUE RESUELVE
  • Sin gateway, cada servicio expone su propio host y puerto: la seguridad y los límites se implementan N veces.
  • Los clientes quedan acoplados a la topología interna: mover o dividir un servicio rompe a todos los consumidores.
Spring Cloud Gateway Kong NGINX Traefik AWS: Amazon API Gateway
CÓMO FUNCIONA
  1. El cliente llama a una sola URL pública: /api/pagos.
  2. El gateway valida la credencial y aplica políticas.
  3. Resuelve la ruta configurada → servicio destino.
  4. Reenvía la petición a una instancia interna.
  5. Regresa la respuesta; registra métricas y log de acceso.

Anatomía · problema 2: cómo se encuentran entre sí

Service Discovery · nombre lógico → instancias vivas

DEFINICIÓN

Registro central y dinámico: traduce un nombre lógico de servicio («pagos») a la lista de direcciones de sus instancias vivas. Es el binding dinámico: el nombre se resuelve a direcciones en el momento de llamar — el papel del DNS, pero dentro del sistema y con direcciones que cambian a cada rato.

PROBLEMA QUE RESUELVE
  • En contenedores las direcciones IP son efímeras: cada arranque asigna una distinta.
  • Al escalar hay N instancias del mismo servicio: una dirección fija no alcanza.
HERRAMIENTAS
Eureka Consul etcd DNS de Kubernetes AWS: Cloud Map
CÓMO FUNCIONA
  1. La instancia arranca y se registra: nombre, IP, puerto.
  2. Renueva su registro con heartbeats (señales periódicas de vida).
  3. Un consumidor pide «pagos» al registro.
  4. Recibe la lista de instancias vivas y reparte entre ellas.
  5. Llama directo a la instancia elegida.
  6. Si el heartbeat no llega en el plazo, la instancia sale del registro.

Anatomía · problema 3: dónde vive la configuración

Config Server · la configuración vive fuera del artefacto

DEFINICIÓN

Servicio que centraliza la configuración de los demás: cada servicio la solicita al arrancar, en lugar de llevarla dentro de su imagen (el paquete inmutable con su código y dependencias).

Problema que resuelve
  • La misma imagen corre en desarrollo, pruebas y producción con valores distintos (URLs, credenciales).
  • Config dentro de la imagen = reconstruir y redesplegar para cambiar un valor.
Spring Cloud Config ConfigMaps (k8s) Vault AWS: AppConfig · Parameter Store
Cómo funciona
  1. El servicio arranca y se identifica: nombre + perfil (dev / prod).
  2. Solicita su configuración al config server.
  3. El config server la lee de su fuente: un repositorio git versionado.
  4. El servicio la aplica y termina de arrancar.
  5. Un cambio de config se recarga sin reconstruir la imagen.

Anatomía · problema 4: qué pasa si el otro está caído

Message Broker · comunicación asíncrona y desacoplada

DEFINICIÓN

Intermediario que almacena y entrega mensajes: los productores publican, los consumidores procesan a su ritmo. Emisor y receptor no tienen que estar vivos al mismo tiempo.

Problema que resuelve
  • Una llamada síncrona acopla disponibilidad: si el receptor está caído o lento, el emisor falla o espera.
  • Un pico de carga se propaga en cascada por la cadena de llamadas.
cola productor / consumidor ack reentrega dead-letter queue
RabbitMQ Kafka (S11) AWS: SQS · Amazon MQ · MSK
Cómo funciona
  1. El productor publica un evento en el broker.
  2. El broker lo persiste en una cola (lista ordenada de mensajes pendientes).
  3. El consumidor lo toma a su propio ritmo.
  4. Al procesarlo con éxito confirma: ack (acuse de recibo).
  5. Sin ack, el broker lo reentrega.
  6. Tras N fallos, el mensaje va a la dead-letter queue (cola aparte para mensajes fallidos) para revisión.

Anatomía · lecturas repetidas sin castigar la base de datos

Caché · patrón cache-aside

DEFINICIÓN

Almacén en memoria para resultados de operaciones costosas: sirve lecturas repetidas en microsegundos sin tocar la base de datos.

PROBLEMA QUE RESUELVE
  • La base de datos es el recurso caro y compartido: cada lectura repetida suma latencia (tiempo de espera) y carga.
  • Datos que se leen mucho y cambian poco (catálogos, sesiones) se recalculan sin necesidad.
  • Lo difícil no es guardar: es invalidar — mantener la caché coherente con la fuente (S9, con medición).
Redis Memcached AWS: ElastiCache hit ratio (proporción de aciertos) TTL (vida máxima de la entrada)
CÓMO FUNCIONA
  1. Llega la primera lectura: el servicio busca la llave en la caché.
  2. Miss: no está. Va a la base de datos.
  3. Guarda el resultado en la caché con un TTL.
  4. Responde.
  5. Llega la misma lectura otra vez: hit — responde desde memoria, sin tocar la BD.

Bloque IV de IV

Los datos

Por qué un sistema distribuido rara vez tiene una sola base de datos — y cómo se elige cada motor.

Datos 1/2 · el principio

Persistencia políglota · cada servicio, su motor; cada motor, su patrón

Definición

Cada servicio elige su motor de datos según su patrón de acceso, y esa base de datos es privada del servicio.

Problema que resuelve
  • Un solo motor para todos los patrones obliga a compromisos en todos: transaccional, catálogo, caché y análisis no piden lo mismo.
  • Una BD compartida acopla los esquemas de los servicios: nadie puede cambiar su modelo sin coordinar con todos los demás.
Regla

Los datos de un servicio se acceden por su API, nunca por su base de datos. La BD compartida entre servicios es el antipatrón clásico de integración.

El costo, explícito
  • No hay joins entre datos de servicios distintos: se componen por API.
  • La consistencia entre servicios deja de ser automática — se vuelve un problema de diseño (S6: consistencia · S12: sagas).

Profundización: S9 — replicación, sharding y el resto de datos distribuidos.

Comunicación · la propiedad que permite reintentar

Idempotencia · N ejecuciones, el mismo estado final

DEFINICIÓN

Una operación es idempotente si ejecutarla varias veces deja el sistema en el mismo estado que ejecutarla una sola vez: f(f(x)) = f(x).

POR QUÉ ES CENTRAL
  • Un timeout (se agotó el tiempo de espera) no distingue entre nunca llegó y se ejecutó pero la respuesta se perdió — visto en S2.
  • La salida práctica es reintentar; reintentar una operación no idempotente duplica efectos: doble cargo, doble correo.
Operación¿Idempotente?
consultar saldo (GET)sí
poner saldo = 500sí
sumar 100 al saldono
crear un pedido (POST)no
CÓMO FUNCIONA
  1. El cliente genera una llave única por operación (un UUID: identificador único universal) y la manda en el header (encabezado HTTP) Idempotency-Key.
  2. El servidor procesa el cargo y guarda llave → resultado.
  3. La respuesta se pierde en la red: para el cliente fue un timeout.
  4. El cliente reintenta con la misma llave.
  5. El servidor reconoce la llave: devuelve el resultado guardado sin volver a ejecutar.

La decisión de hoy · ensayo, al chat

Caso BoleTix

Cuando se vende un boleto, el sistema debe: actualizar el inventario, generar la confirmación, enviar el correo y registrar el dato para análisis.
